## Summary: what was accomplished, what problems were encountered, and how they were solved

At the very beginning of the project, it was decided to build the application using **FSD (Feature-Sliced Design)**.

**Why**

- it teaches how to separate responsibilities between layers (UI, business logic, API, etc.)
- helps avoid chaos in the project
- reduces the likelihood of conflicts within the team (working in the same files)

Now let’s move on to what I managed to implement and use, as well as how and why.

---

### 1. Complex Component

**What was done**

Implemented the test run feature:

- test state management (run-test)
- step-by-step navigation through questions
- storing user answers
- result calculation
- progress display (question X of N + progress bar)
- separate mode for reviewing incorrect answers (incorrect answers)

**Problems that were addressed**

- Where to store the test run state:
  - current question
  - user answers
  - start time
  - whether the test is completed
- How to avoid spreading business logic across the UI

**Solutions**

- Moved state into a separate layer (features/run-test)  
  → isolated business logic from UI

- Implemented a simple store + selectors  
  → controlled state without heavy solutions (Redux, etc.)

- Separated:
  - logic (model/store/selectors)
  - UI (widget)  
    → follows FSD principles and reduces coupling

- Implemented a separate feature:
  show-incorrect-answers  
  → avoided mixing different scenarios in a single component

---

### 2. Rich UI Screens

**What was done**

Implemented full-featured screens:

- Tests List
  - list of tests (cards)
  - progress display (score, status)

- Test Overview
  - test information
  - attempt history
  - actions:
    - start test
    - view incorrect answers

**Problems that were addressed**

- How to combine data from different sources:
  - tests
  - user progress
  - attempts

- How to avoid passing raw data into the UI

**Solutions**

- Using ViewModel
- Introducing an adaptation layer (adapter functions)

Example:

- Test + UserTestProgress → TestCardViewModel

→ UI receives only the necessary data  
→ no dependency on backend structure

---

### 3. Design Patterns

Several design patterns were used, but I will describe only a few of them.

#### 3.1 Facade

**Where it is used**

- loadTestsList
- initTestRun

**Problem**

Without a facade, the upper layer would need to:

- call multiple APIs
- map data
- handle errors
- manage execution order

**Solution**

Creating orchestration functions:

- loadTestsList(userId)

→ hides:

- data loading
- aggregation
- transformation

---

### 3.2 Adapter

**Where it is used**

- buildTestCards
- mapResultViewModel

**Problem**

UI should not depend on:

- full Test
- full Attempt
- unnecessary fields

**Solution**

Transformation:

`Domain Model → ViewModel`

---

### 4. API Layer

**What was done**

API is separated by entities:

- entities/test/api
- entities/user-test-progress/api
- entities/attempt/api

**Problem**

Without separation:

- chaos in requests
- difficult maintenance
- no clear responsibility boundaries

**Solution**

Following FSD:

- data isolation
- scalability
- clear structure

entities → api

## Thoughts / Plans

Not all problems and their solutions are described here, as it is difficult to document everything and it would take a significant amount of time.

The most important things I realized during this project:

- things are not as simple as they may seem at first
- architecture is not something you "read and implement", but an ongoing process

- When I started learning FSD, I thought it would take 1–2 days

- When I started building the quiz component, I thought it would take ~2 weeks

### 1. Complex Component

**Что было сделано**

Реализована фича прохождения теста:

- управление состоянием теста (run-test)

- сохранение ответов пользователя

- Разделил:
  - логика (model/store/selectors)
  - UI (widget)
    → соответствует FSD и снижает связанность
- Реализовал отдельную фичу:
  show-incorrect-answers
  → не смешивал разные сценарии в одном компоненте

### 3. Design Patterns

Я использовал несколько паттернов проектирования, но опишу только несколько из них.

#### 3.1 Facade

**Где использован**

- loadTestsList
- initTestRun

**Проблема**

Без фасада верхний слой должен:

- дергать несколько API
- маппить данные
- обрабатывать ошибки
- управлять последовательностью

**Решение**

Создание orchestration-функций:

- loadTestsList(userId)

→ скрывает:

- загрузку данных
- объединение
- преобразование

---

#### 3.2 Adapter

**Где использован**

- buildTestCards
- mapResultViewModel

**Проблема**

UI не должен зависеть от:

- полного Test
- полного Attempt
- лишних полей

**Решение**

Преобразование:

`Domain Model → ViewModel`

---

#### 4. API Layer

**Что сделано**

Разделены API по сущностям:

- entities/test/api
- entities/user-test-progress/api
- entities/attempt/api

**Проблема**

Без разделения:

- хаос в запросах
- трудно поддерживать
- нет границ ответственности

**Решение**

Следование FSD:

- изоляция данных
- масштабируемость
- понятная структура

entities → api
